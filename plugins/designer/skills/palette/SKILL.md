# 색 팔레트

컨셉을 색으로 옮겨 아티팩트로 증명하고 승인받는다. 공통 규칙(작업 폴더, 토큰 형식, 접근성 기준, 승인 게이트)은 `designer:design` 스킬을 따른다. 이 스킬은 팔레트 단계의 방법만 적는다.

## 1. 컨셉 인터뷰

색을 고르기 전에 다음을 확인한다. 사용자가 이미 말한 것은 다시 묻지 않고, 빠진 것만 한 번에 묻는다.

- 제품: 무엇을 하는 서비스인지, 주 사용자가 누구인지
- 분위기: 형용사 2개에서 4개(예: 신뢰감 있는, 따뜻한, 절제된)
- 제약: 이미 정해진 브랜드 색, 피해야 할 색, 참고 서비스
- 모드: 라이트만인지 다크도 필요한지. 말이 없으면 둘 다 만든다
- 후보 수: 말이 없으면 3개를 만든다

사용자가 참고 서비스 URL 이나 스크린샷을 주면 `hallmark study` 로 디자인 DNA(구조, 서체 조합, 색 앵커)를 뽑아 핵심 색의 출발점으로 삼는다. 픽셀을 베끼지 않고 DNA 만 참고한다. hallmark 가 없으면 참고 자료를 직접 보고 색조와 분위기만 적는다.

기존 `design/<컨셉>/tokens.json` 이 있으면 그 토큰을 기준으로 수정안을 만든다. 새로 만들지 않는다.

## 2. 팔레트 설계

설계 전에 `frontend-design` 스킬(의존 플러그인 `frontend-design@claude-plugins-official`)을 읽고, 거기 적힌 흔한 기본값(크림 바탕에 세리프와 테라코타, 검정 바탕에 형광 강조 등)을 이 브리프의 선택이 아닌 한 피한다. 설치되어 있지 않으면 사용자에게 알리고 설치를 권한다.

후보마다 다음을 모두 정한다. 일부만 정한 후보는 내지 않는다.

0. 핵심 색. `ui-ux-pro-max` 검색으로 제품 유형에 맞는 팔레트와 스타일을 먼저 찾아 본다(`"<제품 유형> <분위기>" --domain color`, `--domain style`). 결과는 색조 출발점일 뿐이고 토큰은 우리 형식으로 만든다. 그다음 4개에서 6개의 핵심 색을 이름과 함께 정하고(예: "장부 네이비", "영수증 종이"), 왜 이 브리프에 맞는지 한 줄씩 적는다. 아래 단계는 전부 여기서 파생한다. 비슷한 다른 브리프에도 똑같이 냈을 색이면 바꾸고, 바꾼 이유를 승인 요청에 적는다.
1. 원시 색 단계. `primary`, `neutral`, `success`, `warning`, `error`, `info` 각각 `50`, `100`, `200`, `300`, `400`, `500`, `600`, `700`, `800`, `900`, `950`. `500` 이 기준색이다. 단계는 밝기가 고르게 변하도록 OKLCH 기준으로 잡는다. `neutral` 은 순수 회색 대신 `primary` 색조를 아주 약하게 섞는다.
2. 의미 토큰. `references/tokens.md` 의 의미 토큰 목록을 모두 라이트와 다크 값으로 채운다. 값은 원시 토큰 별칭만 쓴다.
3. 다크 모드는 라이트를 뒤집지 않는다. 바탕은 `neutral.950` 대신 `neutral.900` 근처처럼 완전한 검정을 피하고, 주 행동색은 라이트보다 한두 단계 밝은 단계(`primary.400`)를 쓴다.
4. 후보끼리는 색조가 분명히 달라야 한다. 같은 색조의 채도 차이만 있는 후보를 여럿 내지 않는다.

후보마다 `design/<컨셉>/tokens.<후보>.json` 으로 저장한다. 승인되면 하나를 `tokens.json` 으로 확정하고 나머지는 지운다.

## 3. 대비 검사

후보마다 검사 스크립트를 돌린다. 의미 토큰의 글자와 바탕 조합을 라이트와 다크 모두 검사해 WCAG AA 통과 여부를 표로 낸다.

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/skills/palette/scripts/contrast.py" design/<컨셉>/tokens.<후보>.json
```

- 실패한 조합이 있으면 원시 단계를 조정해 통과시킨 뒤 다시 돌린다. 조정해도 통과하지 못하는 조합은 아티팩트에 실패로 표시하고 대안을 적는다.
- 스크립트가 보는 것은 대비 수치뿐이다. 색이 컨셉에 맞는지는 직접 판단한다.

## 4. 팔레트 아티팩트

`design/<컨셉>/palette.html` 을 만들어 Artifact 도구로 올린다. 아티팩트를 만들기 전에 `artifact-design` 스킬을 읽는다. 한 아티팩트에 모든 후보를 넣고 탭이나 세로 구획으로 나눈다.

후보마다 다음을 보여 준다.

1. 컨셉 한 줄과 후보 이름. 후보 이름은 색이 아니라 느낌을 담은 말로 짓는다(예: "차분한 네이비").
2. 원시 색 단계. 색조별로 한 줄, 각 칸에 단계 번호와 hex 값.
3. 의미 토큰. 라이트와 다크를 나란히 두고 토큰 이름을 적는다.
4. 맥락 미리보기. 같은 작은 화면 조각(카드, 주 버튼, 보조 버튼, 본문과 보조 글자, 입력창, 상태 뱃지 4종)을 라이트와 다크로 나란히 그린다. 이 조각은 의미 토큰 CSS 변수만 쓴다.
5. 대비 표. 3절 결과를 통과와 실패로 표시한다.

- 색 값은 CSS 변수 선언 블록에만 두고 본문에서는 변수만 쓴다. 변수 이름 규칙은 `references/tokens.md` 를 따른다.
- 페이지 상단에 라이트와 다크 전환 버튼을 둔다.
- 올린 뒤 사용자에게 링크와 함께 후보별 한 줄 차이를 알려 주고 어느 것으로 갈지 묻는다.

## 5. 수정과 승인

- 사용자 피드백은 토큰 파일을 고친 뒤 같은 `palette.html` 을 다시 만들어 같은 URL 로 올린다. 아티팩트를 손으로 고치지 않는다.
- 사용자가 승인하면 선택된 후보를 `tokens.json` 으로 저장하고 `$extensions.daljin.status` 를 `approved`, `approvedAt` 을 오늘 날짜로 적는다. 다른 후보 파일은 지운다.
- 승인된 뒤 "레이아웃은 `designer:layout` 으로 이어서 할 수 있다" 고 한 줄 알린다. 사용자가 요청하기 전에 레이아웃을 시작하지 않는다.
