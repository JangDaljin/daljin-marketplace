# 레이아웃

승인된 토큰만으로 화면을 그려 아티팩트로 증명하고 승인받는다. 공통 규칙(작업 폴더, 토큰 형식, 화면 폭과 경계선, 접근성, 승인 게이트)은 `designer:design` 스킬을 따른다.

## 1. 시작 조건

- `design/<컨셉>/tokens.json` 의 `$extensions.daljin.status` 가 `approved` 여야 한다. 아니면 멈추고 `designer:palette` 로 승인을 먼저 받는다. 사용자가 "그냥 레이아웃부터" 라고 해도 같다.
- 간격, 글자, 모서리 토큰이 아직 없으면 2절에서 먼저 정한다.

## 2. 간격, 글자, 모서리 토큰

처음 레이아웃을 만들 때 `tokens.json` 에 다음을 추가한다. 이미 있으면 그대로 쓴다.

| 그룹 | 기본값 | 규칙 |
| --- | --- | --- |
| `space` | `1`=4px, `2`=8px, `3`=12px, `4`=16px, `5`=20px, `6`=24px, `8`=32px, `10`=40px, `12`=48px, `16`=64px | 4px 배수만. 이 밖의 간격은 쓰지 않는다 |
| `font.size` | `caption`=12, `body-sm`=14, `body`=16, `title-3`=20, `title-2`=24, `title-1`=32, `display`=40 | 본문 16px 기준 |
| `font.weight` | `regular`=400, `medium`=500, `bold`=700 | |
| `font.lineheight` | `tight`=1.25, `normal`=1.5 | 제목은 tight, 본문은 normal |
| `radius` | `sm`=6, `md`=12, `lg`=20, `full`=9999 | |
| `motion.duration` | `fast`=120ms, `normal`=200ms, `slow`=320ms | 모션을 쓸 때만 추가 |
| `motion.easing` | `enter`=cubic-bezier(0, 0, 0.2, 1), `exit`=cubic-bezier(0.4, 0, 1, 1), `move`=cubic-bezier(0.4, 0, 0.2, 1) | 들어올 때 enter, 나갈 때 exit |
| `breakpoint` | `tablet`=768, `pc`=1280 | `designer:design` 4절 |

- 글자체는 컨셉에 맞게 고른다. `ui-ux-pro-max` 로 서체 조합을 검색해(`"<제품 유형> <분위기>" --domain typography`) 출발점을 잡되, 결과에는 한글 서체가 없으므로 본문용 한글 서체는 따로 고른다. 한 가족이나 두 가족까지 쓰고, 둘이면 분명히 달라야 한다. 사용자가 서체에 신경 쓰지 않는다고 했을 때만 Pretendard 와 system-ui 대체를 기본값으로 둔다. 고른 서체와 이유는 토큰 추가와 함께 승인받는다.
- 토큰 추가도 토큰 변경이다. 레이아웃 아티팩트와 함께 보여 주고 같이 승인받는다.

## 3. 화면 인터뷰

화면마다 다음을 확인한다. 사용자가 이미 말한 것은 묻지 않는다.

- 화면 이름과 목적
- 들어갈 내용 블록과 순서
- 상태: 비어 있을 때, 로딩, 오류가 필요한지
- 구간: 말이 없으면 모바일 375, 태블릿 768, PC 1440 셋 다 만든다
- 참고 화면이 있는지
- 화면 성격: 제품 화면(앱 안의 기능 화면)인지 랜딩·마케팅 화면인지. 랜딩·마케팅 화면이면 `hallmark` 의 `references/structure.md` 와 매크로구조 목록을 읽고 히어로, 섹션 리듬, 마무리를 흔한 "히어로, 기능 3개, CTA, 푸터" 순서가 아닌 이 브리프의 구조로 정한다. 제품 화면은 이 절차를 쓰지 않는다

## 4. 화면 레이아웃 아티팩트

화면마다 `design/<컨셉>/layout-<화면>.html` 을 만들어 Artifact 도구로 올린다. 만들기 전에 `artifact-design` 스킬과 `frontend-design` 스킬(의존 플러그인 `frontend-design@claude-plugins-official`)을 읽는다. `frontend-design` 의 기본값 목록(똑같은 둥근 카드 반복, 모든 제목 위의 대문자 라벨, 순서가 아닌 내용의 01/02/03 번호, 섹션마다 등장 애니메이션 등)에 걸리는 것이 있으면 이 브리프의 선택이 아닌 한 바꾼다.

1. 세 구간 프레임을 한 페이지에 가로로 나란히 둔다(모바일, 태블릿, PC 순). 프레임 위에 구간 이름과 폭을 적는다. 창이 좁으면 세로로 쌓인다.
2. 라이트와 다크 전환 버튼을 둔다.
3. 내용은 실제와 비슷한 더미 글과 숫자를 넣는다. "Lorem ipsum" 이나 "텍스트" 같은 자리표시 글을 쓰지 않는다. UI 글은 다음 규칙으로 쓴다.
   - 사용자가 이해하는 말로 이름 붙인다. 시스템 구조 용어(웹훅 설정)가 아니라 사용자가 하는 일(알림 관리)로 쓴다.
   - 버튼은 눌렀을 때 일어나는 일을 그대로 쓴다: "제출" 대신 "변경 사항 저장". 같은 행동은 흐름 내내 같은 이름을 쓴다. "게시" 버튼의 완료 알림은 "게시했어요" 다.
   - 말투는 프로젝트에 정의가 없으면 해요체로 통일한다. 합니다체와 섞지 않는다. 짧은 라벨과 버튼은 명사형("저장", "거래 내역")도 된다.
   - 오류는 무엇이 잘못됐고 어떻게 고치는지 적는다. 사과하지 않고 모호하게 쓰지 않는다. 빈 화면은 다음 행동을 안내한다.
   - 영어 대문자 표기나 가운뎃점으로 이은 메타 정보("A · B · C") 같은 장식 표기를 쓰지 않는다.
4. 그래프나 차트가 들어가면 `dataviz` 스킬을 읽고 그 규칙대로 그린다. 색은 의미 토큰에서 고른다.
5. 모든 색, 간격, 글자 크기, 모서리는 토큰 CSS 변수만 쓴다. 변수 선언 블록은 `tokens.json` 에서 생성한다.
6. 상태 변형(비어 있음, 로딩, 오류)이 있으면 같은 파일 아래쪽에 모바일 폭으로 추가한다.
7. 모션은 상태 전환을 보여 줄 때만 넣는다. 넣을 때는 emil `animate` 스킬을 읽고 이징(들어올 때 ease-out, 나갈 때 ease-in), 길이, `transform` 과 `opacity` 만 쓰는 속성, 중단 가능 여부를 그 규칙대로 정한다. 정한 값은 `motion.duration.*`, `motion.easing.*` 토큰으로 `tokens.json` 에 넣고, 어느 상태 전환에 어느 토큰을 쓰는지 아티팩트의 해당 요소 옆에 적는다. 개발자는 이 값만 보고 구현하므로 적지 않은 모션은 구현되지 않는다. 섹션마다 등장 애니메이션을 넣지 않는다.
8. 모바일 구간은 emil `mobile-native` 스킬의 항목(safe area, 100vh, 입력창 확대, 탭 하이라이트, 끈적이는 hover)을 반영한다.

## 5. 컴포넌트 아티팩트

화면에 두 번 이상 나오거나 상태가 있는 요소는 컴포넌트로 뽑아 `design/<컨셉>/component-<이름>.html` 에 따로 만든다.

- 상태를 가로로 나란히 둔다: default, hover, pressed, disabled, 필요하면 selected, error.
- 마지막에 "최악의 데이터" 변형을 둔다. emil `break-ui` 스킬의 목록대로 아주 긴 이름, 한 글자 이름, 끊기지 않는 이메일, 빈 값, 아주 큰 숫자, 이모지와 라틴 아닌 글자를 넣어 컴포넌트가 깨지지 않는지 보여 준다. 깨지면 토큰이 아니라 레이아웃(줄임, 줄바꿈, 최소 폭)을 고친다. 이 변형은 개발자가 그대로 구현하고 테스트 데이터로 쓰는 명세이므로 Figma 에도 `State=WorstCase` variant 로 올린다.
- 크기 변형(sm, md, lg)이 있으면 세로로 둔다.
- 각 변형 아래에 variant 이름을 적는다. Figma variants 이름과 같게 한다(`State=Pressed`).
- 폭에 따라 모양이 바뀌는 컴포넌트만 구간별로 그린다.

## 6. 토큰 검사

올리기 전에 검사 스크립트를 돌린다. 변수 선언 블록 밖에 색 값, 토큰에 없는 px 값이 있으면 실패한다.

스크립트 경로의 `<이 SKILL.md가 있는 폴더>`를 실제 설치된 이 파일의 폴더 절대 경로로 바꿔 실행한다.

```bash
python3 "<이 SKILL.md가 있는 폴더>/scripts/check-tokens.py" design/<컨셉>/tokens.json design/<컨셉>/layout-<화면>.html
```

- 실패하면 토큰으로 바꾼다. 필요한 값이 토큰에 없으면 2절 토큰 추가로 돌아가고, 색이면 `designer:palette` 로 돌아간다.
- 스크립트는 값만 본다. 정렬, 위계, 여백 리듬은 직접 확인한다.

토큰 검사를 통과하면 다음 점검을 순서대로 돌린다. 설치되지 않은 외부 스킬은 건너뛰고 승인 요청에 건너뛴 사실과 설치 명령을 적는다.

| 순서 | 점검 | 보는 것 |
| --- | --- | --- |
| 1 | `designer:ui-review` | 접근성, 포커스, 폼, 모션, 타이포, 긴 글 처리, 다크 모드, 안티패턴 |
| 2 | `hallmark audit <파일>` | AI 가 만든 티가 나는 기본값(slop test). 지적만 받고 hallmark 가 고치게 두지 않는다 |
| 3 | emil `review-animations` | 모션이 있을 때만. 이징, 길이, 속성, 중단 가능 여부 |
| 4 | `ui-ux-pro-max` `"<화면 성격> <걱정되는 항목>" --domain ux` | 터치 타깃, 내비게이션, 폼 피드백처럼 화면별로 걱정되는 UX 지침 한두 개 |

지적이 남아 있으면 고치고 해당 점검을 다시 돌린다. 의도적 선택이라 고치지 않는 지적은 승인 요청에 이유를 적는다. 점검 결과는 승인 요청에 점검별 한 줄로 요약한다.

## 7. 수정과 승인

- 피드백은 HTML 과 토큰 파일을 고친 뒤 같은 URL 로 다시 올린다.
- 사용자가 화면과 컴포넌트를 승인하면 각 HTML 상단 주석에 `approved: <날짜>` 를 적는다. 승인 안 된 파일은 Figma 에 올리지 않는다.
- 승인된 뒤 "Figma 반영은 `designer:figma-sync` 로 할 수 있다" 고 한 줄 알린다. 요청 전에 Figma 작업을 시작하지 않는다.
