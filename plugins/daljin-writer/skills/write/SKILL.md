# 문서 작성 원칙

사람이 읽는 문서를 쓸 때 지킬 원칙과 작성 순서. 원칙은 모두 지킨다. 원칙끼리 부딪히면 읽는 사람이 더 빨리 이해하는 쪽을 고른다.

## 적용 범위

- 적용: README, 설계 문서, 보고서, 회의록, 위키, PR 설명처럼 사람이 읽는 문서.
- 적용하지 않음: `SKILL.md`, `CLAUDE.md`, 에이전트 프롬프트, 설정 파일처럼 에이전트가 읽고 동작하는 지시문. 지시문은 지시문 형식(명령형, 코드 표기, 코드 블록 허용)으로 쓴다.

## 1. 작성 원칙

1. **필요한 것만 쓴다.** 독자가 이 문서로 할 일에 필요한 것만 남긴다.
   - 할 일이 설치면 설치 명령만 둔다. 구성 설명, 동작 원리, 부가 실행 방법은 요청이 없으면 넣지 않는다.
   - 독자가 사용자 본인뿐이면 이미 아는 배경과 이유를 쓰지 않는다.
   - 공개 문서에는 비공개 저장소 구조, 인증 방법 같은 내부 정보를 쓰지 않는다.
   - 절을 통째로 지워도 독자의 할 일에 지장이 없으면 그 절은 지운다.
2. **두괄식.** 문서, 절, 문단 모두 결론을 첫 문장에 둔다.
3. **사람이 읽기 편하게.** 처음 보는 사람 기준으로 약어와 내부 별칭을 풀어 쓴다. 소리 내어 읽었을 때 자연스러워야 한다.
4. **부드러운 말투.** 문장은 "~해요", "~예요"처럼 부드러운 존댓말로 끝낸다. 제목, 목록 항목, 표 칸은 짧은 명사형도 된다.
5. **한 줄에 한 가지.** 전달이 목적인 글은 한 줄에 한 가지만 쓴다. 나열은 목록으로 쓴다. 마크다운은 줄만 바꾸면 한 문단으로 이어 붙으므로 줄마다 떨어져 보여야 하면 목록이나 빈 줄을 쓴다. 길게 풀어 쓰는 글은 예외.
6. **참조는 직접 옮긴다.** "자세한 것은 어디를 보세요"로 끝내지 않고 필요한 부분을 가져와 쓴다. 출처만 남기고 설명을 비우지 않는다.
7. **특수 기호 금지.** 화살표, 줄표, 별표 장식, 체크 표시, 이모지, 가운뎃점, 꺾쇠 괄호를 쓰지 않고 말로 푼다. 제목, 목록, 표 같은 마크다운 구조 문법은 쓴다.
8. **백틱 금지.** 인라인 코드 표기와 코드 블록 펜스를 모두 쓰지 않는다. 제품, 파일, 명령 이름은 그냥 글자로 쓴다. 독자가 입력할 명령은 네 칸 들여쓰기로 보여 준다.
9. **한국어와 영어를 섞지 않는다.** 대신할 한국어가 없는 용어만 영어로 쓴다. 영어 동사에 "하다", "되다"를 붙이지 않는다. 영어 이름 뒤 조사는 읽는 소리에 맞춘다(`daljin-writer을`).
10. **짧고 명료하게.** 분량을 채우려고 늘리지 않는다. 되풀이와 끝맺음 요약을 쓰지 않는다. 지워도 뜻이 같은 문장은 지운다.
11. **강조 표시 금지.** 굵게와 기울임을 쓰지 않는다. 중요한 것은 문장 앞이나 별도 줄에 둔다.
12. **문단을 분명히 끝낸다.** 한 문단에 생각 하나. "등등", "여러 가지가 있어요" 같은 흐린 마무리를 쓰지 않는다.
13. **빈 줄.** 문단 사이, 제목 아래, 목록과 표 앞뒤에 빈 줄 하나. 두 줄 이상 겹치지 않는다.
14. **긴 글의 숫자 목차.** 500자가 넘는 글(공백 포함, 들여쓴 명령과 머리말 제외)은 첫 문단 다음에 목차를 둔다. 목차와 제목에 1, 2, 3 번호를 붙이고 하위 절은 1.1, 1.2로 잇는다.

## 2. 작성 순서

1. 독자와 목적을 정한다. 누가 읽고 읽은 뒤 무엇을 해야 하는지, 공개 문서인지 본인만 보는 문서인지 정한다. 정할 수 없으면 사용자에게 묻는다.
2. 독자의 할 일에 필요한 절만 뼈대로 잡고, 각 절의 결론 문장을 먼저 쓴다.
3. 참조 자료를 직접 읽고 필요한 부분만 옮긴다.

   | 자료 | 도구 |
   | --- | --- |
   | PDF, Word, PowerPoint, Excel | `markitdown` MCP의 `convert_to_markdown` |
   | 웹 페이지 | WebFetch |
   | Confluence, Jira | mcp-atlassian |
   | 개인 지식베이스 | `daljin-kb:search` 스킬 |

4. 본문을 쓴 뒤 필요 없는 절부터 지우고, 그다음 문장과 단어를 줄인다.
5. 점검한다. 파일로 저장했다면 점검 스크립트를 돌린다. 길게 풀어 쓰는 글이면 `--long-form`을 붙인다.

   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/skills/review/scripts/lint.py" [--long-form] <파일 경로>
   ```

   스크립트는 겉모양만 본다. "위반 없음"은 좋은 글이라는 뜻이 아니다. 1번 원칙(필요한 것만)과 두괄식은 직접 확인한다. 전체 점검 절차는 `/daljin-writer:review`를 따른다.

## 3. 예시

README를 쓸 때, 독자가 본인뿐이고 할 일이 설치라면 결과물은 이것으로 충분하다.

```markdown
# daljin-marketplace

    claude plugin marketplace add NomaDamas/k-skill
    claude plugin marketplace add JangDaljin/daljin-librarian
    claude plugin marketplace add JangDaljin/daljin-marketplace
    claude plugin install daljin-writer@daljin-marketplace
```

사람에게 변경을 알리는 글이라면 다음처럼 고친다.

고치기 전:

```text
이번 배포에서는 여러 가지 변경사항이 있었는데, 자세한 내용은 PR을 참조하시면 되고, 가장 중요한 건 **인증 방식 변경**입니다 → 기존 토큰은 만료됩니다.
```

고친 후:

```text
이번 배포로 인증 방식이 바뀌어서 기존 토큰은 모두 만료돼요.
다시 로그인해야 해요.

바뀐 점은 두 가지예요.

1. 토큰 유효 기간이 30일에서 7일로 줄었어요.
2. 갱신 토큰을 새로 발급해요.
```
