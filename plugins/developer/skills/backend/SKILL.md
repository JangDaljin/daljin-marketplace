# 백엔드 공통 규칙

모든 서버 작업에 적용하는 공통 규칙이다. 언어와 프레임워크별 구현 방법은 언어별 하네스(`developer:java`, `developer:nestjs`)에 있다. 두 서버를 서로 똑같이 맞추지 않는다. 공통 규칙만 여기에 두고, 기술별 구현은 각 하네스를 따른다. 이 스킬과 언어별 하네스가 부딪히면 사용자에게 묻는다.

## 0. 프로젝트 규칙 우선

가장 먼저 적용하는 규칙이다.

- 작업 중인 프로젝트에 정의된 규칙이 있으면 그 규칙을 따르고, 이 스킬과 언어별 하네스의 같은 항목은 무시한다. 1절 작업 흐름도 예외가 아니다.
- 프로젝트 규칙에는 다음이 들어간다: `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING.md` 같은 문서, 린트와 포맷 설정, 빌드와 CI 설정, 이미 코드에 자리 잡은 구조와 관례.
- 프로젝트에 정의가 없는 항목에만 이 스킬과 언어별 하네스를 적용한다.
- 작업을 시작할 때 프로젝트 규칙을 먼저 확인하고, 하네스와 다른 점을 사용자에게 알린다. 프로젝트 규칙을 하네스에 맞게 바꾸지 않는다.

## 1. 작업 흐름

모든 작업은 설계, 승인, 구현과 테스트, 코드 리뷰, 커밋 순서로 진행한다. 단계를 건너뛰지 않는다.

### 1.1 설계 보고와 승인

- 코드를 쓰기 전에 설계를 사용자에게 보고하고, 사용자가 허락한 뒤에만 코드를 작성한다. 작은 수정도 같다.
- 설계 보고에는 다음을 넣는다.
  - 무엇을 왜 바꾸는지
  - 바꿀 파일과 새로 만들 파일
  - API, DB 스키마, DTO 변경
  - 작성할 테스트 목록
  - 정해지지 않았거나 확인이 필요한 점
- 허락 전에는 파일을 만들거나 고치지 않는다. 코드를 읽고 조사하는 일은 해도 된다.
- 구현 중에 설계와 달라져야 하면 멈추고 바뀐 설계를 다시 보고해 허락받는다.

### 1.2 테스트

- 테스트 코드 작성은 강제다. 기능 추가와 버그 수정에는 반드시 테스트를 함께 쓴다.
- 버그 수정은 버그를 재현하는 실패 테스트를 먼저 쓰고, 고친 뒤 통과하는지 확인한다.
- 테스트가 없거나 실패하면 작업을 완료로 보지 않고, 코드 리뷰와 커밋으로 넘어가지 않는다.

### 1.3 커밋 전 코드 리뷰

커밋하기 전에 서브에이전트로 자체 코드 리뷰를 한다.

1. Agent 도구로 `developer:code-reviewer` 서브에이전트를 띄운다. 작업한 컨텍스트와 분리해 새 눈으로 보게 하기 위해서다. 심각도 기준과 보고 형식은 에이전트에 정해져 있다. 프롬프트에 다음을 넣는다.
   - 리뷰할 변경 범위(`git diff` 대상)
   - 따를 규칙 파일 경로: 프로젝트 규칙 파일, 이 스킬과 해당 언어별 하네스의 SKILL.md
   - 작업 목적과 승인된 설계 요약
2. 리뷰 결과를 사용자에게 보고한다. 지적마다 심각도, 위치(`파일:줄`), 문제, 고칠 방법을 적고 critical 부터 정렬한다. 지적이 없으면 없다고 보고한다.
3. 어떤 지적을 고칠지 사용자에게 묻는다. 묻기 전에는 고치지 않는다.
4. 사용자가 고르라고 한 지적만 고친다. 고르지 않은 지적은 고치지 않고 남겨 둔다.
5. 수정한 뒤 테스트와 언어별 하네스의 검증 명령을 다시 통과시키고 커밋한다.

| 심각도 | 기준 | 예시 |
| --- | --- | --- |
| critical | 데이터 손실, 보안 취약점, 장애, 핵심 기능의 잘못된 결과 | 인증 누락, SQL 인젝션, 트랜잭션 누락으로 데이터 불일치, Entity 그대로 노출 |
| major | 특정 상황에서 기능이 틀리거나 성능, 유지보수에 실제 문제가 생김. 이 규칙 위반 | 예외 경로 누락, N+1 쿼리, 요청 형식 검사 누락, 테스트 누락, Swagger 누락 |
| minor | 동작에는 영향이 없는 품질 문제 | 이름, 가독성, 중복, 주석 |

### 1.4 리팩터링

- 리팩터링은 사용자가 허락할 때만 한다. 기능 작업 중에 임의로 하지 않는다.
- 기능 작업 중 리팩터링할 곳을 발견하면 고치지 말고 기록해 두었다가, 기능 커밋이 끝난 뒤 사용자에게 제안한다.
- 리팩터링은 기능 커밋이 끝난 뒤 반드시 별도 커밋으로 한다. 기능 변경과 리팩터링을 절대 한 커밋에 넣지 않는다.
- 리팩터링도 1.1 설계 승인, 1.2 테스트, 1.3 코드 리뷰를 똑같이 거친다. 리팩터링 전후로 기존 테스트가 모두 통과해야 한다.

### 1.5 커밋 메시지

- 개발자들이 통용하는 타입을 앞에 붙이고 한 줄로 간단히 쓴다: `feat: 로그인 개발`
- 본문은 기본으로 쓰지 않는다.

| 타입 | 쓰는 경우 |
| --- | --- |
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작을 바꾸지 않는 구조 개선 (1.4 의 별도 커밋) |
| `test` | 테스트만 추가하거나 고침 |
| `docs` | 문서 |
| `chore` | 빌드 설정, 의존성, 잡무 |
| `bump` | 버전 올림 |
| `perf` | 성능 개선 |
| `ci` | CI 설정 |

## 2. 데이터베이스

- 기본은 PostgreSQL 이다.
- 사용자가 지정했거나 연동할 기존 시스템이 MySQL 이면 MySQL 을 쓴다.
- 그 밖의 데이터베이스가 필요해 보이면 쓰기 전에 사용자에게 묻는다.
- 통합 테스트도 운영과 같은 데이터베이스로 돌린다. H2, SQLite 같은 대체 DB 로 바꿔 돌리지 않는다.

### 2.1 이름 규칙

| 대상 | 규칙 | 예시 |
| --- | --- | --- |
| 컬럼 | snake_case | `user_id` |
| 시간을 나타내는 컬럼 | `_at` 으로 끝낸다 | `created_at`, `deleted_at`, `last_login_at` |
| 누구인지 나타내는 컬럼 | `_by` 로 끝낸다 | `created_by`, `approved_by` |
| 기본 키 | `pk_` 로 시작한다: `pk_<테이블>` | `pk_orders` |
| 외래 키 | `fk_` 로 시작한다: `fk_<테이블>_<컬럼>`. 기본은 만들지 않는다(2.3) | `fk_orders_user_id` |
| 인덱스 | `idx_` 로 시작한다: `idx_<테이블>_<컬럼>` | `idx_orders_user_id` |
| 유니크 키 | `uk_` 로 시작한다: `uk_<테이블>_<컬럼>` | `uk_users_email` |

- 기본 키, 외래 키, 인덱스, 유니크 키는 DB 가 자동으로 짓게 두지 않고 항상 이름을 직접 정한다.
- 여러 컬럼에 걸치면 컬럼 이름을 순서대로 잇는다: `idx_orders_user_id_created_at`
- 외래 키는 참조 테이블이 아니라 컬럼 이름으로 짓는다. 같은 테이블을 여러 번 참조해도(`created_by`, `approved_by`) 이름이 겹치지 않게 하기 위해서다.

### 2.2 코멘트

- 모든 테이블과 모든 컬럼에 DB 코멘트를 반드시 단다. 코멘트가 없는 테이블이나 컬럼을 만들지 않는다.
- 컬럼을 추가하거나 의미를 바꾸는 마이그레이션에는 코멘트 추가와 수정도 함께 넣는다.
- 코멘트는 짧은 한국어로 쓴다: `회원`, `주문 금액`, `탈퇴 시각`
- 이름만으로 알 수 없는 정보는 코멘트에 넣는다.
  - 상태, 코드 컬럼은 허용 값과 뜻: `주문 상태 (PENDING: 결제 대기, PAID: 결제 완료, CANCELED: 취소)`
  - 단위: `할인율 (%)`, `응답 시간 (ms)`
  - 비어 있을 때의 뜻: `탈퇴 시각 (NULL 이면 활동 중)`

### 2.3 테이블 사이의 참조

- ORM 에 연관관계를 선언하지 않는다. JPA 의 `@ManyToOne`, `@OneToMany`, `@OneToOne`, `@ManyToMany`, Prisma 의 관계 필드(`@relation`)를 쓰지 않는다.
- 다른 테이블은 id 컬럼(`user_id`)으로 논리적으로만 참조한다. Entity 에도 id 값(`userId`)만 둔다.
- 물리 FK 제약은 만들지 않는다. 사용자가 특정 테이블에 FK 를 요청할 때만 만들고, 이름은 2.1 의 `fk_` 규칙을 따른다.
- 테이블을 함께 읽어야 하면 쿼리에서 id 로 조인하거나, 나눠 조회한 뒤 id 로 묶는다.
- 참조 컬럼은 조회 패턴을 보고 인덱스(`idx_`)를 건다. FK 가 없어 DB 가 인덱스를 대신 만들어 주지 않는다.

### 2.4 시간

- DB 에 저장하는 시각은 모두 UTC 기준이다.
- PostgreSQL 은 `timestamptz` 타입을 쓴다. MySQL 은 `DATETIME` 에 UTC 값을 저장하고 커넥션 타임존을 UTC(`+00:00`)로 둔다.
- 애플리케이션도 DB 와 주고받을 때 UTC 로 변환한다. 서버 기본 타임존에 기대지 않는다.

### 2.5 감사 컬럼

- 모든 테이블에 `created_at`, `updated_at` 을 둔다. 둘 다 NOT NULL 이다.
- 사용자가 만들거나 바꾸는 테이블에는 `created_by`, `updated_by`(사용자 id)를 둔다.
- 감사 컬럼 값은 공통 장치(JPA Auditing, repository 공통 처리 등)가 채운다. 서비스 코드에서 직접 넣지 않는다.
- 삭제는 기본으로 물리 삭제다. 복구나 이력이 필요한 테이블만 `deleted_at` 으로 soft delete 한다.
  - soft delete 테이블은 모든 조회에 `deleted_at IS NULL` 조건을 넣는다.
  - 유니크 키가 삭제된 행과 부딪히지 않게 한다. PostgreSQL 은 `WHERE deleted_at IS NULL` 부분 유니크 인덱스를 쓴다.

## 3. API 문서 (Swagger)

- 모든 Controller 와 엔드포인트에 Swagger 문서를 빠짐없이 작성한다. 문서가 없는 엔드포인트는 완료로 보지 않는다.
- 엔드포인트마다 요약(summary), 요청 형식, 성공 응답, 주요 실패 응답 코드를 적는다.
- 설명은 간결하게, 필요한 것만 적는다.
  - 요약은 한 줄로 끝낸다: `회원 목록 조회`
  - 상세 설명은 요약만으로 동작을 알 수 없을 때만 적는다.
  - 필드 이름을 되풀이하는 설명은 쓰지 않는다. `email` 필드에 "이메일" 이라고 적지 않는다. 형식, 단위, 허용 값처럼 이름만으로 알 수 없는 정보만 적는다.

## 4. DTO

- Entity(ORM 모델)를 API 응답으로 절대 그대로 내보내지 않는다. 요청도 Entity 로 바로 받지 않는다. 항상 Request/Response DTO 를 거친다.
- 별도 지시가 없으면 DTO 필드 이름과 JSON 키는 camelCase 를 쓴다. snake_case 같은 다른 규칙은 사용자가 지시했거나 외부 시스템 계약이 요구할 때만 쓴다.
- Request DTO 는 형식 검사가 필수다. 모든 필드에 다음 중 해당하는 제약을 건다.
  - 필수 여부
  - 타입, 길이, 숫자 범위
  - 형식: 이메일, URL, 날짜, 정규식, 허용 값 목록(enum)
- 형식 검사에 실패하면 400 으로 응답하고, 어느 필드가 왜 틀렸는지 에러 응답의 `details` 에 담는다(5절).
- 검사 제약은 Swagger 문서에도 드러나게 한다(필수 여부, 길이, 허용 값).
- 날짜와 시각은 ISO 8601 UTC 문자열로 응답한다. JavaScript `toISOString()` 형식이 기준이다: `2026-10-14T08:00:00.000Z`
- 요청의 날짜와 시각도 ISO 8601 문자열로 받고 형식을 검사한다. 오프셋이 붙어 오면(`+09:00`) UTC 로 바꿔 처리한다.
- 날짜 형식이 틀리거나 JSON 이 깨져 요청 본문을 읽지 못해도 400 으로, 5절 형식으로 응답한다.

## 5. 에러 응답

모든 에러는 같은 형식으로 응답한다.

| 필드 | 내용 |
| --- | --- |
| `statusCode` | HTTP 상태 코드 |
| `message` | 사람이 읽을 에러 설명 한 줄 |
| `details` | 추가 정보. 형식 검사 실패면 필드별 오류 목록, 없으면 빈 배열 |
| `stack` | 스택 트레이스. 개발용 환경에서만 넣는다 |

```json
{
  "statusCode": 400,
  "message": "요청 형식이 올바르지 않습니다",
  "details": [
    { "field": "email", "reason": "이메일 형식이 아닙니다" }
  ],
  "stack": "..."
}
```

- 개발용 환경에서는 `stack` 에 스택 트레이스를 넣어 보낸다.
- 실배포 환경에서는 `stack` 필드를 아예 내보내지 않는다. 값을 비우는 것이 아니라 키를 빼야 한다.
- 실배포 환경의 500 응답 `message` 에는 내부 정보(예외 원문, SQL, 클래스 이름)를 넣지 않고 일반 문구를 쓴다. 원래 내용은 서버 로그에만 남긴다.
- 개발용 환경인지는 코드에 박지 않고 설정값(환경 변수, 프로필)으로 판단한다. 설정이 없으면 실배포 환경으로 본다.
- 이 형식은 전역 예외 처리기 한 곳에서 만든다. Controller 마다 따로 만들지 않는다. 404, 본문 파싱 실패처럼 프레임워크가 만드는 오류도 이 형식으로 바꾼다.
- 프레임워크나 라이브러리의 오류 원문(영어 메시지, 내부 경로)을 `message` 로 그대로 내보내지 않는다. 정한 문구로 바꾼다.
- Swagger 의 실패 응답 스키마도 이 형식으로 적는다.

## 6. 최초 프로젝트 구성

새 서버 프로젝트를 구성할 때 CORS 를 처음부터 설정한다.

- 구성 전에 사용자에게 확인한다: 브라우저에서 직접 호출하는 클라이언트가 있는지, 환경별 허용 출처(origin)가 무엇인지, 쿠키 같은 인증 정보를 보내는지.
- 허용 출처는 코드에 박지 않고 환경 변수나 설정 파일에서 읽는다.
- 운영 환경에서 `*` 를 허용하지 않는다. 인증 정보를 보내면 어느 환경에서도 `*` 를 쓰지 않는다.
- 허용 메서드와 헤더는 실제로 쓰는 것만 연다.

## 7. API 설계

### 7.1 URL 과 메서드

- 경로는 복수 명사와 kebab-case 로 쓴다: `/users`, `/order-items`
- 소유 관계만 한 단계 중첩한다: `/users/{userId}/orders`
- 경로에 동사를 넣지 않는다. 리소스로 표현하기 어려운 상태 변경만 하위 경로 동사를 허용한다: `POST /orders/{orderId}/cancel`
- 쿼리 파라미터는 camelCase 로 쓴다: `?createdFrom=...`
- API 버전 접두사(`/v1`)는 프로젝트가 정하지 않았으면 붙이지 않는다. 호환되지 않는 변경이 필요하면 설계 단계에서 사용자에게 묻는다.

| 메서드 | 쓰는 경우 |
| --- | --- |
| `GET` | 조회. 상태를 바꾸지 않는다 |
| `POST` | 생성, 상태 변경 행위 |
| `PUT` | 전체 교체 |
| `PATCH` | 일부 수정 |
| `DELETE` | 삭제 |

### 7.2 상태 코드

| 코드 | 쓰는 경우 |
| --- | --- |
| 200 | 조회, 수정 성공 |
| 201 | 생성 성공. 생성한 리소스를 응답한다 |
| 204 | 성공했지만 본문이 없음(삭제) |
| 400 | 요청 형식 오류(5절 `details`) |
| 401 | 인증 없음, 인증 실패 |
| 403 | 권한 없음 |
| 404 | 리소스 없음 |
| 409 | 중복, 현재 상태와 충돌(이미 취소된 주문 취소) |
| 422 | 형식은 맞지만 비즈니스 규칙 위반(잔액 부족) |
| 500 | 처리하지 못한 서버 오류 |
| 502 | 외부 API 실패(8절) |
| 504 | 외부 API 시간 초과(8절) |

### 7.3 응답 본문과 페이지네이션

- 단건은 객체를 그대로 응답한다. `{ "data": ... }` 처럼 감싸지 않는다.
- 목록은 페이지 객체로 응답한다. 기본은 페이지 번호 방식이다.
  - 요청: `page`(1부터), `size`(기본 20, 최대 100)
  - 응답: `{ "items": [...], "page": 1, "size": 20, "totalCount": 135, "totalPages": 7 }`
- 무한 스크롤이나 데이터가 많아 전체 개수를 세기 부담스러우면 커서 방식을 쓴다.
  - 요청: `cursor`(처음엔 생략), `size`
  - 응답: `{ "items": [...], "nextCursor": "..." }`. 다음이 없으면 `nextCursor` 는 `null` 이다.
- 정렬은 `sort=<필드>,<asc|desc>` 로 받는다: `sort=createdAt,desc`. 허용한 필드만 받고 나머지는 400 으로 응답한다.

## 8. 외부 API 호출

- 외부 서비스마다 클라이언트를 하나씩 만든다. 기본 URL 과 타임아웃은 설정값에서 읽는다.
- 연결 타임아웃과 읽기 타임아웃을 반드시 정한다. 라이브러리 기본값(무제한)에 맡기지 않는다.
- 시간 초과는 504, 그 밖의 외부 실패는 502 로 바꿔 5절 형식으로 응답한다. 외부 오류 원문, 요청 헤더, 외부 URL 을 응답에 넣지 않는다.
- 우리 서버의 request id, 내부 식별자, 사용자 토큰을 외부 호출에 넘기지 않는다. 외부 API 가 요구하는 값과 인증 정보만 보낸다.
- 외부 API 는 트랜잭션 밖에서 부른다. 안에서 부르면 응답을 기다리는 동안 DB 커넥션을 붙잡는다.
- 외부 응답 타입을 정의한다. 테스트에서 실제 외부 API 를 부르지 않는다.

## 9. 운영

### 9.1 request id

- 요청마다 request id 를 정해 모든 로그에 찍는다.
- `x-request-id` 헤더가 있고 형식(영문, 숫자, 하이픈 64자 이하)에 맞으면 그 값을 쓰고, 아니면 UUID 를 만든다. 형식을 검사하지 않으면 줄바꿈 같은 값으로 로그를 위조할 수 있다.
- request id 는 우리 서버 로그에만 쓴다. 외부 호출에 넘기지 않는다(8절).

### 9.2 헬스 체크와 정상 종료

- 헬스 체크 엔드포인트를 둔다. 인증 없이 열되 버전, 설정, DB 주소 같은 내부 정보를 내보내지 않는다.
- 종료 신호(SIGTERM)를 받으면 새 요청을 받지 않고, 처리 중인 요청을 마친 뒤 DB 연결을 닫고 종료한다.

### 9.3 보안 헤더

- 모든 응답에 보안 헤더를 붙인다: `X-Content-Type-Options: nosniff`, `X-Frame-Options`, `Strict-Transport-Security` 등.
- 요청 수 제한(rate limit)은 애플리케이션에서 구현하지 않는다.

### 9.4 운영 환경의 Swagger

- `production` 프로필에서는 Swagger UI 와 API 문서 경로를 끈다. `local`, `develop` 에서만 연다.

### 9.5 배포

- 컨테이너 이미지에 `TZ=Asia/Seoul` 을 넣어 로그 시각을 한국 시간으로 찍는다. DB 저장 시각과 API 응답 시각은 이와 상관없이 UTC 다(2.4절, 4절).
- CI 는 push 와 PR 마다 린트, 타입 검사, 단위 테스트, 통합 테스트를 모두 돌린다. 통합 테스트는 CI 에서 Testcontainers 로 실제 DB 를 띄운다.
- 비밀값은 이미지나 저장소에 넣지 않고 배포 환경의 환경 변수로 넣는다.

## 10. 인증과 인가

- 인증 방식(JWT, 세션 등)은 프로젝트마다 다르다. 설계 단계(1.1)에서 확인하고, 정해지지 않았으면 임의로 고르지 않고 사용자에게 묻는다.
- 인증과 권한 검사는 Controller 에 들어가기 전 공통 장치(가드, 필터)에서 한다. 리소스 소유자 확인(내 주문인지)은 Service 에서 한다.
- 인증이 없거나 실패하면 401, 권한이 없으면 403 으로 응답한다.
- 감사 컬럼의 `created_by`, `updated_by` 는 인증된 사용자 id 로 채운다(2.5절).
