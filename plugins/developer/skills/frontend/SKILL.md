# 프론트엔드 공통 규칙

모든 프론트엔드 구현에 적용하는 공통 규칙이다. 서버 작업의 공통 규칙은 `developer:backend` 에 있고, 이 스킬은 그 짝이다. 프레임워크별 구현 방법은 하네스(`developer:nextjs`)에, 스타일과 컴포넌트 라이브러리는 `developer:design-library` 에, 디자이너가 넘긴 디자인을 받아 구현하는 절차는 `developer:implement-design` 에 있다. 이 스킬과 하네스가 부딪히면 사용자에게 묻는다.

## 0. 프로젝트 규칙 우선

- 작업 중인 프로젝트에 정의된 규칙이 있으면 그 규칙을 따르고, 이 스킬과 하네스의 같은 항목은 무시한다. 1절 작업 흐름도 예외가 아니다.
- 프로젝트 규칙에는 `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING.md`, 린트와 포맷 설정, 빌드와 CI 설정, 이미 자리 잡은 구조와 관례, 이미 쓰고 있는 컴포넌트 라이브러리가 들어간다.
- 작업을 시작할 때 프로젝트 규칙을 먼저 확인하고, 하네스와 다른 점을 사용자에게 알린다. 프로젝트를 하네스에 맞게 바꾸지 않는다.

## 1. 작업 흐름

설계, 승인, 구현과 테스트, UI 검토, 커밋 순서로 진행한다. 단계를 건너뛰지 않는다.

### 1.1 설계 보고와 승인

- 코드를 쓰기 전에 설계를 보고하고 허락받은 뒤에만 쓴다. 작은 수정도 같다.
- 설계 보고에 넣는 것: 구현할 화면과 컴포넌트, 참조할 디자인 원본(Figma 프레임과 노드 또는 아티팩트 파일), 쓸 라이브러리 컴포넌트와 새로 만들 컴포넌트, 바꿀 파일과 새 파일, 데이터 흐름(서버 컴포넌트인지 클라이언트인지, API 호출 위치), 작성할 테스트, 정해지지 않은 점.
- 허락 전에는 파일을 만들거나 고치지 않는다. 코드와 Figma 를 읽는 일은 해도 된다.

### 1.2 테스트

- 기능 추가와 버그 수정에는 반드시 테스트를 함께 쓴다. 컴포넌트는 렌더링과 상호작용 테스트, 화면 흐름은 E2E 테스트다.
- 버그는 재현하는 실패 테스트를 먼저 쓰고 고친다.
- 테스트가 없거나 실패하면 완료로 보지 않는다.

### 1.3 커밋 전 UI 검토

커밋 전에 다음을 순서대로 돌리고 결과를 사용자에게 보고한다.

| 순서 | 검토 | 보는 것 |
| --- | --- | --- |
| 1 | `developer:ui-review` | 접근성, 포커스, 폼, 모션, 타이포, 긴 글 처리, 다크 모드, hydration, 안티패턴 |
| 2 | 화면 비교 | 구현 화면 스크린샷과 디자인 원본(Figma 프레임 또는 아티팩트)을 나란히 보고 다른 점을 적는다(`developer:implement-design` 5절) |
| 3 | 하네스 검증 명령 | 린트, 타입 검사, 테스트, 빌드 |

지적은 심각도, 위치(`파일:줄`), 문제, 고칠 방법을 적고 critical 부터 정렬한다. 어떤 지적을 고칠지 사용자에게 묻고, 고른 것만 고친 뒤 검증을 다시 통과시키고 커밋한다.

| 심각도 | 기준 |
| --- | --- |
| critical | 접근성 차단(키보드로 못 씀, 라벨 없는 입력), 데이터 노출, 깨진 화면, Figma 와 다른 정보 구조 |
| major | 특정 상황에서 틀림(긴 글, 빈 상태, 다크 모드), 포커스 없음, reduced motion 무시, Figma 와 다른 색·간격·글자, 테스트 누락 |
| minor | 이름, 가독성, 중복 |

### 1.4 리팩터링

사용자가 허락할 때만, 기능 커밋 뒤 별도 커밋으로 한다. 기능 변경과 섞지 않는다.

### 1.5 커밋 메시지

타입을 앞에 붙이고 한 줄로 쓴다: `feat: 거래 목록 화면 구현`. 본문은 기본으로 쓰지 않는다. 타입은 `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `style`(시각 변경만), `perf`, `ci`.

## 2. 디자인 원본은 디자이너의 결과물

개발자는 디자인을 하지 않는다. 디자이너 페르소나(`designer`)가 넘긴 결과물을 그대로 구현한다. 원본은 다음 순서로 찾고, 여러 개가 있으면 앞의 것이 우선이다.

| 순서 | 원본 | 위치 |
| --- | --- | --- |
| 1 | Figma 디자인 모음집(Variables, Components, Screens) | `design/<컨셉>/figma.md` 의 URL |
| 2 | 승인된 아티팩트와 토큰 파일 | `design/<컨셉>/tokens.json`, `layout-*.html`, `component-*.html` |
| 3 | 사용자가 준 HTML 시안이나 이미지 | 사용자가 지정한 파일 |

- 색, 간격, 글자 크기, 모서리, 모션(길이, 이징, 바뀌는 속성)을 코드에서 새로 정하지 않는다. 원본의 토큰을 CSS 변수로 옮기고(`developer:implement-design` 3절) 컴포넌트는 그 변수만 쓴다.
- 원본에 없는 화면, 상태, 모션이 필요하면 만들지 말고 사용자에게 알린다. 디자인을 추가하는 것은 디자이너의 일이다.
- 원본이 틀렸거나 구현 불가능해 보여도 코드에서 조용히 고치지 않는다. 사용자에게 알리고 디자이너가 원본을 고친 뒤 다시 읽는다.
- 원본이 하나도 없으면 코드에서 디자인을 정하지 않는다. 사용자에게 알리고 `designer` 페르소나로 디자인을 먼저 만들게 한다. 급해서 임시로 구현해야 하면 색과 간격을 토큰 파일 하나에 모아 두고 "디자인 미확정" 이라고 보고에 적는다.

## 3. 스타일과 컴포넌트 라이브러리

스타일링과 컴포넌트 라이브러리(Tailwind, shadcn/ui, UI 유틸)의 규칙은 `developer:design-library` 에 있다. 컴포넌트를 추가하거나 스타일을 쓰거나 토큰을 코드로 옮길 때 그 스킬을 따른다. 프레임워크 고유 내용은 하네스(`developer:nextjs`)에 있다.

## 4. 접근성과 품질 바닥선

Figma 에 보이지 않아도 다음은 항상 지킨다. `developer:ui-review` 가 검사한다.

- 키보드만으로 모든 기능을 쓸 수 있고 포커스가 보인다. `outline: none` 은 대체 포커스 표시가 있을 때만.
- 입력에는 라벨, 아이콘 버튼에는 `aria-label`, 이미지에는 `alt`.
- 본문 대비 4.5:1, UI 경계 3:1. 색만으로 상태를 구분하지 않는다.
- `prefers-reduced-motion` 을 존중한다.
- 긴 글, 빈 목록, 큰 숫자, 한 글자 이름에서 깨지지 않는다. 디자이너가 컴포넌트 아티팩트에 둔 "최악의 데이터" 상태를 그대로 구현하고 그 데이터로 테스트한다.
- 모바일 768px 미만, 태블릿 768px 이상, PC 1280px 이상에서 동작한다. 경계선은 프로젝트나 Figma 토큰이 정한 값이 우선이다.
- 터치 타깃 44px 이상, safe area 처리, 확대 금지 금지.

## 5. 모션

- 모션은 디자인 원본에 적힌 것만, 적힌 값(길이, 이징, 바뀌는 속성)대로 구현한다. 토큰은 `motion.*`(`developer:implement-design` 3절)이다. 원본에 없는 모션을 넣지 않는다.
- 구현 규칙: `transform` 과 `opacity` 만 움직이고, `transition: all` 을 쓰지 않으며, 사용자 입력에 중단될 수 있게 하고, `prefers-reduced-motion` 이면 끄거나 줄인다.
- 프레임이 떨어지면 레이아웃과 페인트를 일으키는 속성(`width`, `height`, `top`, `box-shadow`)을 움직이고 있는지 먼저 본다.

## 6. UI 글

- 프로젝트에 정의가 없으면 해요체로 통일한다. 합니다체와 섞지 않는다. 짧은 라벨과 버튼은 명사형도 된다.
- 버튼은 눌렀을 때 일어나는 일을 쓴다. 같은 행동은 흐름 내내 같은 이름이다.
- 오류는 무엇이 잘못됐고 어떻게 고치는지 쓴다. 빈 화면은 다음 행동을 안내한다.
- Figma 에 적힌 문구가 있으면 그대로 쓴다. 바꿔야 하면 사용자에게 알린다.

## 7. 프론트엔드가 하지 않는 일

- 색과 레이아웃을 새로 디자인하지 않는다. 디자인은 `designer` 페르소나의 일이다.
- 서버 API 구현은 `developer:backend` 와 언어별 하네스를 따른다. 한 작업에 서버와 화면이 다 있으면 두 공통 규칙을 모두 부른다.
- 백엔드 API 를 설계하지 않는다. 계약이 없으면 사용자에게 묻는다.
- 모션의 느낌, 라이브러리의 생김새, 빈 상태의 문구 같은 디자인 판단을 하지 않는다. 원본에 없으면 디자이너에게 돌린다.
