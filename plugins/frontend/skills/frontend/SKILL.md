# 프론트엔드 공통 규칙

모든 프론트엔드 구현에 적용하는 공통 규칙이다. 프레임워크별 구현 방법은 하네스(`frontend:nextjs`)에, Figma 를 코드로 옮기는 절차는 `frontend:handoff` 에 있다. 이 스킬과 하네스가 부딪히면 사용자에게 묻는다.

## 0. 프로젝트 규칙 우선

- 작업 중인 프로젝트에 정의된 규칙이 있으면 그 규칙을 따르고, 이 스킬과 하네스의 같은 항목은 무시한다. 1절 작업 흐름도 예외가 아니다.
- 프로젝트 규칙에는 `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING.md`, 린트와 포맷 설정, 빌드와 CI 설정, 이미 자리 잡은 구조와 관례, 이미 쓰고 있는 컴포넌트 라이브러리가 들어간다.
- 작업을 시작할 때 프로젝트 규칙을 먼저 확인하고, 하네스와 다른 점을 사용자에게 알린다. 프로젝트를 하네스에 맞게 바꾸지 않는다.

## 1. 작업 흐름

설계, 승인, 구현과 테스트, UI 검토, 커밋 순서로 진행한다. 단계를 건너뛰지 않는다.

### 1.1 설계 보고와 승인

- 코드를 쓰기 전에 설계를 보고하고 허락받은 뒤에만 쓴다. 작은 수정도 같다.
- 설계 보고에 넣는 것: 구현할 화면과 컴포넌트, 참조할 Figma 프레임과 노드, 쓸 shadcn/ui 컴포넌트와 새로 만들 컴포넌트, 바꿀 파일과 새 파일, 데이터 흐름(서버 컴포넌트인지 클라이언트인지, API 호출 위치), 작성할 테스트, 정해지지 않은 점.
- 허락 전에는 파일을 만들거나 고치지 않는다. 코드와 Figma 를 읽는 일은 해도 된다.

### 1.2 테스트

- 기능 추가와 버그 수정에는 반드시 테스트를 함께 쓴다. 컴포넌트는 렌더링과 상호작용 테스트, 화면 흐름은 E2E 테스트다.
- 버그는 재현하는 실패 테스트를 먼저 쓰고 고친다.
- 테스트가 없거나 실패하면 완료로 보지 않는다.

### 1.3 커밋 전 UI 검토

커밋 전에 다음을 순서대로 돌리고 결과를 사용자에게 보고한다.

| 순서 | 검토 | 보는 것 |
| --- | --- | --- |
| 1 | `frontend:ui-review` | 접근성, 포커스, 폼, 모션, 타이포, 긴 글 처리, 다크 모드, hydration, 안티패턴 |
| 2 | `emil-skills:review-animations` | 모션이 있을 때만 |
| 3 | 화면 비교 | 구현 화면 스크린샷과 Figma 프레임을 나란히 보고 다른 점을 적는다(`frontend:handoff` 5절) |
| 4 | 하네스 검증 명령 | 린트, 타입 검사, 테스트, 빌드 |

지적은 심각도, 위치(`파일:줄`), 문제, 고칠 방법을 적고 critical 부터 정렬한다. 어떤 지적을 고칠지 사용자에게 묻고, 고른 것만 고친 뒤 검증을 다시 통과시키고 커밋한다.

| 심각도 | 기준 |
| --- | --- |
| critical | 접근성 차단(키보드로 못 씀, 라벨 없는 입력), 데이터 노출, 깨진 화면, Figma 와 다른 정보 구조 |
| major | 특정 상황에서 틀림(긴 글, 빈 상태, 다크 모드), 포커스 없음, reduced motion 무시, Figma 와 다른 색·간격·글자, 테스트 누락 |
| minor | 이름, 가독성, 중복 |

### 1.4 리팩터링

사용자가 허락할 때만, 기능 커밋 뒤 별도 커밋으로 한다. 기능 변경과 섞지 않는다.

### 1.5 커밋 메시지

타입을 앞에 붙이고 한 줄로 쓴다: `feat: 거래 목록 화면 구현`. 본문은 기본으로 쓰지 않는다. 타입은 `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `style`(시각 변경만), `perf`, `ci`.

## 2. 디자인 원본은 Figma

디자이너 페르소나(`designer`)가 Figma 에 승인된 디자인만 모아 둔다. 그 파일이 색, 간격, 글자, 컴포넌트, 화면 구조의 단일 원본이다.

- 색, 간격, 글자 크기, 모서리 값을 코드에서 새로 정하지 않는다. Figma Variables 에서 읽어 CSS 변수로 옮기고(`frontend:handoff` 3절), 컴포넌트는 그 변수만 쓴다.
- Figma 에 없는 화면이나 상태가 필요하면 만들지 말고 사용자에게 알린다. 디자인을 추가하는 것은 디자이너의 일이다.
- Figma 가 틀렸거나 구현 불가능해 보여도 코드에서 조용히 고치지 않는다. 사용자에게 알리고, 디자이너가 Figma 를 고친 뒤 다시 읽는다.
- Figma 파일 위치는 프로젝트의 `design/<컨셉>/figma.md` 에 있다. 없으면 사용자에게 URL 을 묻는다.
- Figma 가 아예 없는 프로젝트에서는 `frontend-design` 스킬로 디자인 판단을 하되, 그 사실을 보고에 적고 색과 간격은 토큰 파일로 먼저 정리한 뒤 쓴다.

## 3. 컴포넌트는 shadcn/ui 우선

- 컴포넌트 라이브러리는 shadcn/ui 다. Tailwind 는 그 아래 깔리는 스타일링 수단이지 컴포넌트를 손수 짜는 도구가 아니다.
- 필요한 컴포넌트는 먼저 shadcn/ui 에서 찾아 CLI 로 추가한다. 없으면 shadcn/ui 컴포넌트를 조합해 만들고, 그래도 안 될 때만 새로 만든다. 새로 만든 컴포넌트도 shadcn/ui 와 같은 구조(`cva` variant, `cn` 유틸, Radix 또는 Base UI 프리미티브)로 쓴다.
- `components/ui/` 아래 shadcn/ui 가 생성한 파일은 CLI 로 다시 생성할 수 있어야 하므로 손으로 크게 고치지 않는다. 변형이 필요하면 감싸는 컴포넌트를 만든다.
- 다른 컴포넌트 라이브러리(MUI, Chakra, Ant Design 등)는 프로젝트가 이미 쓰고 있을 때만 쓴다. 새로 들이기 전에 사용자에게 묻는다.
- 토스트, 숫자 입력, 차트, 가상 스크롤, 드래그 같은 유틸 라이브러리는 `emil-skills:pick-ui-library` 로 고른다. 손수 만들지 않는다.
- Figma 컴포넌트와 shadcn/ui 컴포넌트의 대응은 `frontend:handoff` 가 `design/<컨셉>/handoff.md` 에 적는다. 같은 Figma 컴포넌트를 두 군데서 다르게 옮기지 않는다.

## 4. 접근성과 품질 바닥선

Figma 에 보이지 않아도 다음은 항상 지킨다. `frontend:ui-review` 가 검사한다.

- 키보드만으로 모든 기능을 쓸 수 있고 포커스가 보인다. `outline: none` 은 대체 포커스 표시가 있을 때만.
- 입력에는 라벨, 아이콘 버튼에는 `aria-label`, 이미지에는 `alt`.
- 본문 대비 4.5:1, UI 경계 3:1. 색만으로 상태를 구분하지 않는다.
- `prefers-reduced-motion` 을 존중한다.
- 긴 글, 빈 목록, 큰 숫자, 한 글자 이름에서 깨지지 않는다. `emil-skills:break-ui` 로 확인한다.
- 모바일 768px 미만, 태블릿 768px 이상, PC 1280px 이상에서 동작한다. 경계선은 프로젝트나 Figma 토큰이 정한 값이 우선이다.
- 터치 타깃 44px 이상, safe area 처리, 확대 금지 금지.

## 5. 모션

- 상태 전환을 보여 주는 모션만 넣는다. 섹션마다 등장 애니메이션을 넣지 않는다.
- 모션을 만들 때는 `emil-skills:animate` 를 읽는다. 들어올 때 ease-out, 나갈 때 ease-in, `transform` 과 `opacity` 만, `transition: all` 금지, 중단 가능.
- 끊기면 `emil-skills:animation-performance` 로 원인을 찾는다.

## 6. UI 글

- 프로젝트에 정의가 없으면 해요체로 통일한다. 합니다체와 섞지 않는다. 짧은 라벨과 버튼은 명사형도 된다.
- 버튼은 눌렀을 때 일어나는 일을 쓴다. 같은 행동은 흐름 내내 같은 이름이다.
- 오류는 무엇이 잘못됐고 어떻게 고치는지 쓴다. 빈 화면은 다음 행동을 안내한다.
- Figma 에 적힌 문구가 있으면 그대로 쓴다. 바꿔야 하면 사용자에게 알린다.

## 7. 프론트엔드가 하지 않는 일

- 색과 레이아웃을 새로 디자인하지 않는다. 디자인은 `designer` 페르소나의 일이다.
- 백엔드 API 를 설계하지 않는다. 계약이 없으면 사용자에게 묻는다.
